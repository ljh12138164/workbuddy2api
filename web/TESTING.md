# 测试与 TDD

## 当前测试

运行 `pnpm test` 使用 Vitest，当前 34 个测试分布在 4 个测试文件中：

- `checks/http.test.ts`：通过 HTTP 与 tRPC 调用检查管理认证、同源限制、网关认证、三种协议、并发配额、流中断记账、绑定隔离和日志分页。

- `checks/phone.test.ts`：短信授权会话的持久化、验证流程及一次性 token。
- `checks/d1.test.ts`：通过环境变量与 D1 HTTP 驱动完成默认登录、管理读写和无效 Key 检查；模拟 Cloudflare HTTP 响应，不替换数据库工厂。

测试使用 Drizzle ORM 连接 Node SQLite 内存数据库，并模拟上游，不调用真实账号、不发短信。HTTP 测试通过替换数据库工厂连接测试数据库；部分既有测试还断言内部租约状态，不能将整个测试集描述为只验证公共接口。密码哈希存储通过数据库接口检查，这是用户明确要求验证的持久化结果。

已有测试通过不代表原实现采用了严格 TDD。之前未完整记录每项功能的“先失败，再实现，再通过”过程，也没有自动化浏览器交互测试。界面此前通过浏览器检查，类型检查与构建属于额外验证。

## 后续改动的 TDD 流程

先确认用户可观察的行为及测试入口。对于管理访问方式，使用 `/api/trpc/*` 的 HTTP 入口作为验证边界：

1. 每次只为一个行为编写测试，运行它并记录预期失败。
2. 实现让该测试通过的最小改动，不通过模拟认证结果使测试直接通过。
3. 运行该测试及现有回归测试，再进行类型检查。
4. 有界面改动时补充构建和实际浏览器验证；不能用构建通过替代行为测试。

新增行为测试通过接口状态码及响应验证结果，避免查询数据库或断言私有函数来代替用户可观察的行为。
